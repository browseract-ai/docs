# Architecture

BrowserAct gives an Agent one CLI model for different browser environments. The Agent can use the same commands whether it opens a normal browser, a local Chrome connection, or a stealth browser.

## Browser types

| Type | Best for | Main tradeoff |
| --- | --- | --- |
| `chrome` | Reusing local Chrome or Edge login state in a separate browser instance | Imported profile data is a snapshot, not live sync |
| `chrome-direct` | Enterprise SSO, certificates, browser extensions, or the user's real Chrome environment | Highest permission level because the Agent controls the user's active Chrome |
| `stealth` | Protected sites, proxy use, private mode, or large-scale collection | Hosted capabilities require an API Key |

## Shared CLI model

All browser types use the same basic interaction loop:

```bash
browser-act --session s1 browser open <browser-id> https://example.com
browser-act --session s1 state
browser-act --session s1 click 2
browser-act --session s1 input 3 "text"
browser-act --session s1 screenshot ./shot.png
```

The Agent first reads page state, then acts on indexed elements.

## Browser data model

Common fields:

| Field | Meaning |
| --- | --- |
| `id` | The browser identifier used by CLI commands |
| `name` | Human-readable browser name |
| `type` | `chrome`, `chrome-direct`, or `stealth` |
| `desc` | A natural-language description the Agent can use to pick a browser |
| `confirm_before_use` | Whether the Agent must ask before using this browser |

`desc` helps the Agent choose the right browser. After a browser is used for a new purpose, the Agent can append to the description:

```bash
browser-act browser update <id> --desc-append "Also used for order tracking"
```

## Browser selection

1. Use a browser whose `desc` clearly matches the task.
2. If there is only one available browser, use it when it is safe.
3. If several browsers could match, ask the user.
4. Ask before sensitive operations or when `confirm_before_use` is set.

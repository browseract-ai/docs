# Security Model

BrowserAct gives an Agent real browser control. The safety model is based on clear confirmation, session ownership, local data handling, and careful use of high-permission browser modes.

## Confirmation rules

Ask the user before sensitive operations:

| Operation | Why it needs confirmation |
| --- | --- |
| Create or delete a browser | Creates or removes a persistent automation endpoint |
| Import a profile | Copies login-related browser state |
| Change proxy settings | Changes network identity |
| Change private mode | Changes fingerprint and persistence behavior |
| Change `confirm_before_use` | Changes the safety policy |
| Use a `confirm_before_use` browser | The browser may access sensitive accounts |

Confirmation happens in the conversation. The Agent should explain what it is about to do, then wait for approval.

## Data handling

BrowserAct is designed to keep normal browser automation data local: cookies, login state, page content, screenshots, network capture, and browser profiles stay on the user's machine unless a command explicitly saves or shares data.

The clear exception is `solve-captcha`, which sends the CAPTCHA challenge image to BrowserAct service for solving. It should not include cookies, full page content, or the page URL.

## Session ownership

Sessions can share login state within the same browser, but navigation, tabs, and network capture are separate. An Agent should only operate sessions it created.

```bash
browser-act session list
browser-act --session my-task session close my-task
```

## chrome-direct permissions

`chrome-direct` controls the user's active Chrome. It can access logged-in sessions, certificates, and extensions in that browser. Explain the risk and ask before using it.

## Safe usage tips

- Observe the page with read-only commands before taking action.
- Use offline mode to test risky submit flows when appropriate.
- Pause browser commands during remote assist.
- Close sessions when the task is done.
